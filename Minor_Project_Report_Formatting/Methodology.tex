\chapter{METHODOLOGY}

\section{Overview}
The Smart Gym Assistant is developed as an embedded sensing and machine-learning
system. Two MPU6050 sensors collect body-motion data, and an ESP32 processes the
readings to identify supported exercises and posture states. The system also counts
completed repetitions and provides feedback through an OLED display, a buzzer, and
a web dashboard. The current implementation focuses on bicep curls and squats.

The methodology covers the feasibility of the system, its requirements, data flow,
KNN model-training pipeline, live operation, application deployment, and evaluation.
The design is modular so additional exercises can be added later by collecting new
labeled data and regenerating the embedded model.

\section{Feasibility Analysis}
\subsection{Technical Feasibility}
The system is technically feasible because the ESP32 can communicate with two
MPU6050 sensors over I2C, process a compact KNN model, connect to Wi-Fi, and drive
the OLED and buzzer. The model uses twelve numeric sensor features and a limited set
of representative prototypes, which keeps live inference practical on the
microcontroller.

\subsection{Economic Feasibility}
The prototype uses low-cost and widely available components: an ESP32 board, two
MPU6050 modules, an OLED display, and a buzzer. The software tools are open-source
or freely available for educational use. Therefore, the system can be developed and
maintained at a lower cost than camera-based commercial fitness systems.

\subsection{Operational Feasibility}
The system is simple to operate. The user places the sensors consistently, connects
the ESP32 to Wi-Fi, and selects either data-collection mode or live mode. Results are
shown locally on the OLED and remotely through the browser dashboard. The feedback
does not require a dedicated camera or continuous supervision by a trainer.

	\includegraphics[width=0.58\textwidth]{Graphics/block diagram.png}
	\caption{Conceptual block diagram of the Smart Gym Assistant.}
	\label{fig:system-block}
\end{figure}

The original conceptual figure uses the general terms ``motion sensor'' and
``microcontroller.'' In the implemented prototype, these correspond to two MPU6050
modules and the ESP32. The implemented output devices are the SH1106 OLED and the
buzzer; the web dashboard is reached through the ESP32 Wi-Fi connection and FastAPI.

\subsection{Data Collection}
The two MPU6050 sensors are connected to the ESP32 through the I2C bus. The first
sensor uses address \texttt{0x68} and the second uses address \texttt{0x69}. The
AD0 pins are configured differently so both sensors can share the same SDA and SCL
lines. Each reading contains three acceleration and three gyroscope values from each
sensor, forming the twelve-feature vector
\begin{equation}
\mathbf{x}(t) = [a_{x1},a_{y1},a_{z1},g_{x1},g_{y1},g_{z1},
a_{x2},a_{y2},a_{z2},g_{x2},g_{y2},g_{z2}].
\end{equation}

The collector task samples the sensors every 20 milliseconds. Each sample is
timestamped and written to the active buffer. After 50 samples, the completed
buffer is passed to the processing or upload task.

\subsection{Detection Engine}
The detection engine standardizes the twelve features and compares the live vector
with the stored KNN prototypes. The squared Euclidean distance is
\begin{equation}
d(\mathbf{x},\mathbf{y}) = \sum_{i=1}^{12}(x_i-y_i)^2.
\end{equation}
The five nearest prototypes vote for the sample label. The majority label across a
50-sample batch becomes the final live prediction. The label combines exercise and
posture, such as \texttt{bicep\_good}, \texttt{bicep\_bad}, \texttt{squat\_good}, or
\texttt{squat\_bad}.

\subsection{Response System}
The response system displays the detected exercise, posture, and confidence on the
OLED. It can activate the buzzer for bad posture. In live mode, the result is also
sent to FastAPI, which makes the latest exercise, posture, confidence, and online
state available to the web dashboard.

\section{Data Flow for Data-Collection Mode}
Data-collection mode is used to create labeled training data. The user selects the
exercise and posture through the ESP32 web interface or the serial command. The
collector then reads both sensors, creates timestamped samples, and stores them in
alternating buffers.

When a buffer reaches 50 samples, the uploader serializes the batch as JSON and
sends it using an HTTP POST request to the FastAPI endpoint. The payload contains
the user, exercise, posture, and sensor samples. FastAPI validates the payload and
appends each sample to the labeled CSV file. The resulting data is later used by the
Python training script.

\section{Data Flow for Live Mode}
Live mode uses the same sensor-acquisition path but does not append raw samples to
the training CSV. Once a 50-sample buffer is complete, the ESP32 runs KNN inference
for every sample. The label with the highest batch vote is selected, and confidence
is calculated as
\begin{equation}
C = \frac{V_{\mathrm{winner}}}{N},
\end{equation}
where $V_{\mathrm{winner}}$ is the winning vote count and $N$ is the number of
samples in the batch.

The ESP32 updates the OLED and buzzer locally, prints the result to the serial
monitor, and sends the prediction to the live-prediction endpoint. The browser
dashboard receives the latest status through the FastAPI service. This mode keeps
the classification decision on the ESP32 and prevents predicted labels from being
mistaken for ground-truth training labels.

\section{Block Diagram for Training the KNN Model}
The KNN training pipeline begins with labeled CSV data and ends with an embedded
header file. The major stages are:
\begin{figure}[H]
\centering
\includegraphics[width=0.72\textwidth]{Graphics/knn_training_pipeline.png}
\caption{KNN model training pipeline.}
\label{fig:knn-training-pipeline}
\end{figure}

\begin{enumerate}
	\item read the selected training CSV;
	\item remove repeated headers and invalid sensor rows;
	\item separate the twelve sensor features from the metadata and label;
	\item calculate the mean and scale of each feature;
	\item standardize the feature values;
	\item select representative prototypes for every label;
	\item evaluate different values of $k$ and prototype counts; and
	\item generate \texttt{knn\_model.h} for the ESP32.
\end{enumerate}

For a feature $x_i$, standardization is performed using
\begin{equation}
z_i = \frac{x_i-\mu_i}{\sigma_i},
\end{equation}
where $\mu_i$ and $\sigma_i$ are calculated from the training prototypes. The
generated header stores normalized prototypes, labels, means, and scales in program
memory. The ESP32 therefore performs inference without Python or a separate
machine-learning library.

\subsection{Training Dataset}
The current dataset is collected directly from the ESP32 and contains timestamped
records with user, exercise, posture, combined label, and twelve sensor features.
The implemented training scope is bicep curls and squats. Push-ups and other
exercises can be supported later by collecting their labeled good and bad posture
records and rerunning the training pipeline.

\subsection{Model Evaluation}
The notebook uses a stratified validation split so every available class is
represented in training and validation data. It compares multiple values of $k$
and different prototype counts. Performance is reported using accuracy, precision,
recall, F1-score, a parameter-performance graph, and a normalized confusion matrix.

\section{Application Deployment}
The ESP32 firmware is compiled and uploaded using Arduino IDE. The sketch contains
the sensor collector, KNN model interface, OLED and buzzer logic, Wi-Fi connection,
and web-server handlers. The generated \texttt{knn\_model.h} file must be kept in
the same Arduino sketch folder as the firmware files.

The FastAPI application runs on a computer connected to the same local network as
the ESP32. The server receives collection batches at
\texttt{/api/sensor-data}, accepts live predictions at the live-prediction endpoint,
and serves the dashboard from the root URL. The ESP32's server address must use the
computer's local network IP address rather than \texttt{localhost}.

\section{System Evaluation}
The integrated prototype is evaluated in the following order:
\begin{enumerate}
	\item verify that both MPU6050 sensors respond at their configured I2C addresses;
	\item verify that the ESP32 connects to Wi-Fi and reaches the FastAPI server;
	\item check that collection batches contain valid timestamps, labels, and twelve features;
	\item compare KNN predictions with the known exercise and posture condition;
	\item check repetition counts against manually counted movement cycles;
	\item verify OLED, buzzer, serial, and dashboard feedback; and
	\item measure classification accuracy, posture precision and recall, confidence, update delay, and communication reliability.
\end{enumerate}

This evaluation distinguishes model errors from hardware, network, and user-interface
errors. It also provides a clear baseline for improving the model when additional
users or exercises are added.
